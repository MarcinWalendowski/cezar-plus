# Brief: run the default workflow with every step on codex

**Task id:** a15215ef-8be0-4d75-93ed-16c15d638864
**Step:** Gather the record only. No spec, code, or tests were written or run.
**Date:** 2026-08-24

## The problem, in this repository's own terms

The owner's task: *"add a way to run our default workflow only via codex (as different variant?) (every step via codex)"*.

Today, choosing "codex" for a run does not make every step of the default workflow (`spec-to-deploy`) run on codex. Two of its steps carry their own hardcoded `runner` pin that wins over whatever the run picked, and even a step with no pin can still land on the wrong provider because of a separate, previously-documented pool-routing gap. There is also no existing concept of a named workflow "flavor" anywhere in the schema or the UI — "variant" is already a taken product term for something unrelated (parallel re-runs of the *same* task, not a different provider policy). A spec here has to decide both a mechanism (new field? new workflow name? run-level flag?) and, first, whether "every step" is meant to override a deliberate prior policy decision that intentionally keeps two of those steps off codex.

## What the record already decided

1. **`spec-to-deploy` *is* "the default workflow."** `DEFAULT_WORKFLOW_NAME = SPEC_TO_DEPLOY_WORKFLOW.name` and `DEFAULT_WORKFLOW = SPEC_TO_DEPLOY_WORKFLOW`. [packages/cezar/src/workflows/types.ts:1490,1495]. `quick-task` is a separate, still-registered built-in (`QUICK_TASK_WORKFLOW`, [types.ts:412-424]) with a single unnamed step and **zero runner pins** — it already goes wherever the run's own runner points, no change needed there. The KB's `notion-b4c0fb9e0a22` ("quick-task now reads as 'default' everywhere") is about a **display label** change on 2026-08-16 and predates and is superseded by the 2026-08-19 decision that actually swapped the code-level default to `spec-to-deploy` (`.ai/specs/2026-08-19-spec-to-deploy-default-workflow.md`). Treat `DEFAULT_WORKFLOW_NAME` in code as current truth over the older KB note.

2. **Two of the nine `spec-to-deploy` steps are deliberately pinned OFF whatever the run picked, and this was a corrected, owner-driven decision, not an oversight.** `spec`: `runner: SPEC_AUTHORING_RUNNER` where `SPEC_AUTHORING_RUNNER = 'claude' as const'` [types.ts:751,769,1073]. `review-spec`: `runner: 'codex'`, `model: CODEX_REVIEW.model /* gpt-5.6-sol */`, `effort: 'xhigh'` [types.ts:848,1116-1121]. The doc comment at [types.ts:745-750] quotes the owner directly: *"writing spec + spec review should be by opus always, the rest can be load balanced by codex or claude sonnet"* (2026-08-22, correcting an earlier 2026-08-21 "sonnet writes, opus reviews" policy — KB `notion-4f2df2939b43`/`notion-5e72103be90f`). **This is the central tension for "every step via codex": a literal reading directly contradicts a standing, twice-corrected owner instruction that `spec` must stay on Claude opus.** Note also a live inconsistency worth flagging to the owner rather than silently resolving: the comment says spec+review-spec are "opus always," but the code now pins `review-spec` to `codex`/`gpt-5.6-sol`, not opus — `run.ts`'s own comment at [run.ts:6293-6295] is stale, still describing both steps as pinned to claude+opus. This drifted after `.ai/specs/2026-08-24-default-workflow-ten-stages.md` (see point 5) moved `review-spec` to codex SOL xhigh but the run.ts comment wasn't updated.

3. **The other seven steps (`context, implement, run-tests, commit-push, merge, document, deploy`) carry no `runner` at all** — confirmed by direct read of [types.ts:999-1442]. They already follow `taskBackend`, so starting a run with `runner: 'codex'` already sends 7 of 9 steps to codex today. The only steps that need new machinery are `spec` (and, if the owner's "opus always" instruction is meant to survive, `review-spec` should probably stay pinned regardless of a codex-only toggle too — open question, see below).

4. **Provider resolution, exact mechanism and precedence** — all in `packages/cezar/src/workflows/run.ts`:
   - Run level: `taskBackend: RunnerId = chosen?.provider ?? input.runner ?? config.defaultRunner` [run.ts:5068], where `chosen` comes from account-pool resolution (`resolvePoolForDispatch`, [run.ts:5053-5066]) and `config.defaultRunner` defaults to `'claude'` (`packages/cezar/src/config.ts`).
   - Step level: `const backend = (pinned ? await this.downgradePinnedRunner(runId, step, pinned) : undefined) ?? step.runner ?? taskBackend` [run.ts:6304], where `pinned = step.runner`.
   - **`downgradePinnedRunner` can silently move a pinned step OFF the requested provider when every account of that provider is out of quota** — this is deliberate ("never block a task," [run.ts:6292-6301], `.ai/specs/2026-08-23-never-block-a-task.md`): *"availability outranks the pin."* A strict "every step via codex" guarantee is therefore in tension with this policy too — if codex is fully rate-limited, does the codex-only workflow block the run, or silently fall back to claude and no longer be "codex only"? The spec must decide this explicitly rather than inherit the ambiguity.
   - The step schema already supports everything a per-step pin needs: `runner?: RunnerId` and `byRunner?: Partial<Record<RunnerId, {model?, effort?}>>` on `workflowStepSchema` [types.ts:26-99, ~61-84]. `spec`'s `byRunner: { codex: CODEX_COMPLEX }` [types.ts:1074] already names a codex fallback model/effort for exactly the case where `spec` runs on codex — so the raw ingredient to run `spec` on codex well (not just "whatever codex defaults to") already exists in the constant table, just currently unused because the runner pin overrides it.

5. **In-flight, partial work already restructured this exact workflow's step count and model policy — read it before designing anything new.** `.ai/specs/2026-08-24-default-workflow-ten-stages.md`, brief `.ai/specs/briefs/2026-08-24-default-workflow-revision.md`. Header status: *"Partial 2026-08-24. Implementation exists in the task worktree. Typecheck and the focused 57-test gate pass, while the full suite has 9 reproduced baseline-failure files and 20 tests; commit and push are blocked, and runtime QA has not run. QA Needed."* Cross-checking against the current worktree (clean, `git status` shows nothing to commit, `HEAD` tracks `origin/main`) shows at least the `review-spec` → codex/SOL-xhigh piece of that spec **has already landed** in `types.ts` (point 2 above), even though the spec file itself still reads "Partial." **This status is stale or the spec covers more ground than what's landed — a spec author touching `spec-to-deploy`'s steps right now must re-verify current landed state against `types.ts` directly, not trust either the spec header or this brief's snapshot.**

6. **No "workflow variant" concept exists anywhere in the schema, loader, or UI.** `workflowDefSchema` is `{ name, description, steps, source: 'built-in'|'file', path? }` — no `variant`/`provider`/`backend`/`profile` field [types.ts:154-190]. The one existing extension point: a project's own `.ai/cezar/workflows/<name>.yaml` with a matching `name` overrides a built-in of the same name at load time (`packages/cezar/src/workflows/load.ts:66-73`); nothing today lets a user pick "the codex flavor of spec-to-deploy" as a distinct selectable option. **"Variant" is already a taken term in the product** for the composer's parallel-run feature (`draft.variants`, "×2/×3" pill, `packages/web/src/routes/new-task.tsx:328-846` — "how many times to run this task in parallel, each gets its own worktree"). A spec proposing this feature should pick different vocabulary (e.g. "codex-only workflow" / "profile" / "flavor") to avoid confusing the two mechanisms in the UI and in code review.

7. **The exact gap this closes was already anticipated and filed as a known follow-up**, in the same comment block that pins `spec` to claude: *"Today that balance is per-run and chosen by hand: cezar has no cross-runner routing, because `pool:*` balances ACCOUNTS WITHIN a provider and the backend is already fixed before the pool is consulted. Filed as its own task, with making this whole table configurable in global settings."* [types.ts:762-767]. This confirms the request is a recognized, expected extension — not a new idea in tension with the architecture — but also confirms **no design for it exists yet**; "configurable in global settings" is the only steer given, and it doesn't by itself resolve whether that's a global default-runner-for-all-steps setting, a named workflow clone, or a per-run flag.

8. **A composer control for provider selection already exists** (`EnginePills`/`RunnerPill`, `packages/web/src/components/engine-pills.tsx`), which sets `input.runner` for the whole run. It is shown "when there is a choice to make: more than one runner" [engine-pills.tsx:196-198]. Whatever mechanism this spec proposes should account for how it surfaces there — a checkbox next to the existing runner pill, a distinct workflow-name entry, etc. — since that's the only place a user currently expresses "run this on codex."

## Prior decisions this would contradict, or must explicitly reconcile

- **Owner instruction 2026-08-22**, "writing spec + spec review should be by opus always" — a codex-only workflow that forces `spec` (and arguably `review-spec`) onto codex is a direct override of this, not an extension of it. The spec must either (a) treat this as the owner knowingly asking for a stricter, opt-in override for a specific use case, and say so explicitly, or (b) design the codex-only mode to still leave `spec`/`review-spec` on claude/opus (i.e. "every step via codex" means "every step that doesn't already have a deliberate cross-provider pin"). This is a real fork in the design, not a wording nit, and should be surfaced to the owner rather than guessed.
- **`.ai/specs/2026-08-23-never-block-a-task.md`** ("availability outranks the pin") — any hard "codex only, no exceptions" guarantee needs to state how it interacts with the existing downgrade-on-quota-exhaustion behavior.
- **The in-flight `.ai/specs/2026-08-24-default-workflow-ten-stages.md`** — touches the same steps (adds a `merge` stage, moves things around); landing a codex-only mechanism at the same time as that lands risks merge/step-id conflicts. Check its actual current state (not just its header) before scoping phases.

## Open questions a spec will have to settle

1. Does "every step via codex" override the owner's explicit opus-always pin on `spec`/`review-spec`, or exempt those two steps? (See "Prior decisions" above — likely needs a direct owner check rather than an assumption.)
2. Mechanism: a new field on `WorkflowDef`/`workflowStepSchema` (e.g. a `forceRunner` applied at run start that strips/overrides every step's `runner`), a second named built-in workflow (e.g. `spec-to-deploy-codex`) registered alongside the existing three in `load.ts`, or a run-level-only flag that doesn't touch the workflow schema at all?
3. Naming — avoid "variant" (already means parallel re-runs in the composer UI); needs a term that reads unambiguously next to the `×2/×3` variants pill.
4. How does this interact with `downgradePinnedRunner`'s "availability outranks the pin" policy — does codex-only hard-fail when codex is unavailable, or silently downgrade like every other pin does today?
5. Does this apply only to `spec-to-deploy`, or should the mechanism be generic enough to cover `quick-task`/`note-to-spec`/any custom `.ai/cezar/workflows/*.yaml` too? (`quick-task` needs no change since it has zero pins already — worth stating explicitly so the spec doesn't do needless work there.)
6. UI surface: a toggle next to the existing `EnginePills` runner picker, a distinct workflow-picker entry, both, or CLI/API-only for now?
